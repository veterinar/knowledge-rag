# Критерии: детерминированный teardown chroma перед свипом сайдкаров

SDD: class MEDIUM, mode bugfix. Основание — reseal-20260828: build падает
exit 14 в 3 попытках из 3 (r1/r2 27–28.08 ночь, r3 утро — см. логи
kr-reseal-20260828-build*.log), на 204-док корпусе; вчерашний 175-док
проходил со 2-й попытки. Локализовано чтением байтов рантайма 6f12710:
`generation_cli.py` child вызывает `orch.close(strict=True)` →
`chroma_client.close()`, который лишь декрементит refcount общей System;
кэш `SharedSystemClient._identifier_to_system` держит вторую ссылку по
тому же path → sqlite-коннект жив → WAL/SHM переживают close → свип
(немедленный rglob, без ожидания) честно валит build. Зелёный исход —
выигранная GC-гонка; с ростом корпуса вероятность падает.

Линза context7 (chromadb 1.5.9, пин lock): close()/clear_system_cache
семантика — проверить перед пакетом; исход линзы записать в кандидате.

## Критерий 1

В `mcp_server/generation_cli.py` (child), после `orch.close(strict=True)`
и ПЕРЕД свипом сайдкаров добавляется детерминированный дожим:

- `gc.collect()`;
- если сайдкары `chroma_db/chroma.sqlite3-{wal,shm}` ещё существуют —
  короткоживущий `sqlite3.connect(<staging>/chroma_db/chroma.sqlite3)` →
  `PRAGMA wal_checkpoint(TRUNCATE)` → `close()` (population завершена,
  писателей нет; при живом чужом коннекте checkpoint вернёт busy — дожим
  молча уступает и свип честно валит build);
- bounded-wait: до 5 с опроса (~100 мс шаг) на исчезновение сайдкаров,
  по исчезновении — немедленно дальше.

`clear_system_cache` НЕ используется: по байтам пина 1.5.9 он заменяет
кэш пустым словарём БЕЗ `system.stop()` — сиротит живую System и делает
teardown хуже (исход context7-линзы: заменено чтением байтов пина;
`shared_system_client.py:126-129`).

Свип и exit 14 остаются байт-в-байт: гейт не ослабляется. Потолок 5 с —
criteria-решение контролёра, названное здесь (limits.md): ожидание
уже-освобождённого файла, не таймаут гонки.

## Критерий 2

Тест дожим-функции (выделить её в именованную функцию child-скоупа),
двусторонний:

- GREEN-сторона: sqlite-база в WAL-режиме с записями, все коннекты
  закрыты, сайдкары на диске → дожим убирает -wal/-shm;
- RED-сторона (умеет краснеть): второй коннект удерживается открытым →
  дожим НЕ убирает сайдкары, функция сообщает об этом (и свип бы упал).

RED на базе d3782c48: функции нет — тест не собирается/красный.

### Уточнение фикстуры (замер 28.08 на кандидате P1)

Фикстура «создать WAL-базу и закрыть коннект» непригодна: на CPython/macOS
sqlite при close ПОСЛЕДНЕГО коннекта сам чекпойнтит и удаляет -wal/-shm —
GREEN-кейс падал по своему precondition-ассерту (честно, но всегда).
Прод-состояние («сайдкары на диске, база консистентна, писателей нет»)
воспроизводится иначе: subprocess-python открывает WAL-базу, вставляет
строки и умирает через `os._exit(0)` БЕЗ close — файлы остаются, коннектов
нет. GREEN-сторона строится на этой фикстуре; заодно чинится опечатка
`wal_checkpoint(PASS)` (такого режима нет; в kill-фикстуре чекпойнт перед
_exit не нужен вовсе). RED-сторона (живой чужой коннект удерживается)
остаётся как есть — она уже зелёная.

### Дельта P3 (дефект фикса, пойманный RED-тестом 28.08)

`sqlite3.connect` без `timeout` несёт дефолтный busy-таймаут 5 с: на
удержанной чужой транзакции чекпойнт-попытка висела 6.2 с при контрактном
`timeout=1.0`. Правка: `sqlite3.connect(str(db_path), timeout=0.2)` —
попытка дожима не ждёт чужую транзакцию (busy → немедленная уступка), ждёт
только bounded-wait цикл. 0.2 с — criteria-решение контролёра (limits.md):
время на захват свободной базы, не на ожидание занятой.

### Дельта P4 (Devin R1: info-находки 2/3/4; 1 и 6 отклонены с основанием)

- докстринг дожима: «busy → немедленная уступка» уточняется до честного
  «busy-таймаут 0.2 с, затем уступка» (не *immediate*);
- цитата кэша: точные строки `shared_system_client.py:126-129`
  (120-124 — `_release_system`, он как раз зовёт `system.stop()`);
- тест ordering: якорь `orch.close(strict=True)` ловил ПЕРВОЕ вхождение —
  строку комментария; якорь заменяется на однозначный фрагмент фактического
  вызова, чтобы assertion упорядочивал код, а не комментарий.

Отклонено: (1) top-level `sys.path.insert` — предсуществует в базе
d3782c48 (строки 71-73), кандидат его не вносил; (6) CANDIDATE.patch/
digests — артефакты снимка ревью, в кандидате отсутствуют (git status
чист). (5) один checkpoint без ретрая — контрактное решение, названо.
