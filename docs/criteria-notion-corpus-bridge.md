SDD-классификация (skill spec-driven-development): class **HIGH**,
mode **integration** — межконтурный поток данных vetpilot→knowledge-rag
(«Integration is at least HIGH»); отсюда обязательные Delta/Compatibility
ниже, failure modes (коды выхода N1/N5) и rollback (раздел «Активация»).

Delta: corpus стенда получает НОВЫЙ подкаталог `notion-vet/` с манифестом;
ни один существующий corpus-файл не изменяется и не удаляется.
Compatibility: до следующего запечатывания поколения живой индекс и ответы
recall не меняются вовсе (corpus читается только сборкой поколения);
существующие читатели каталога видят добавленный подкаталог — тот же класс,
что уже существующие `general/` и `runtime-probe/`.

Линза context7 (skill source-driven-development §2a), version-sensitive
точка среза — атомарность staging→out через `shutil.move`:
**подтвердила** (индекс `/websites/devdocs_io_python_3_14` = стендовый
python: move = `os.rename` на одном ФС, атомарен; на разных — copy2+rm,
НЕ атомарен). Замер на стенде 27.08: `st_dev(TMPDIR) == st_dev(corpus)`
(16777229 оба) — один том, rename фактический. Известное ограничение:
перенос corpus на другой том сделает move неатомарным; при таком переносе
staging переводится на `dir=` рядом с целью (правка одной строки).
Прочие поверхности среза version-insensitive: формат снимка — наш же
экспортёр vetpilot (читается исходником, линза не о своих байтах);
stdlib json/hashlib — стабильные контракты.

Замеренные основания:

- Экспортёр Notion→файлы УЖЕ существует и не дублируется: `Pet-dog/vetpilot`
  `scripts/notion_export.py` → `knowledge/notion/*.json` + `manifest.json`
  (per-база: database_id, data_source_id, rows, sha256). Направление одно,
  обратной синхронизации нет by design (страница «Ветеринарная память»).
- Снимок в git может отставать от живого Notion (26.08: разборы 19 в снимке
  против 47 живых): свежесть снимка — ритуал экспорта контура VetPilot; мост
  печёт из НАЗВАННОГО коммита и не ходит в сеть.
- corpus живого стенда — markdown-файлы, рекурсивные подкаталоги допустимы
  (`corpus/general/`, `corpus/runtime-probe/` существуют).

## Цель

Записи ветеринарных баз Notion (через git-снимок vetpilot) становятся
корпусными документами knowledge-rag воспроизводимой сборкой с манифестом,
проверкой целостности входа и канарейкой; при следующем запечатывании
поколения они входят в индекс и отвечают через recall указателем на
Notion-страницу.

## Не-цели

- НИКАКОЙ записи в Notion из пайплайна: derived-слой не становится
  источником (эхо-петля запрещена; правило страницы «обратной синхронизации
  нет» сохраняется).
- Экспортёр Notion не трогается и не дублируется (чужой контур vetpilot).
- Пересборка/запечатывание поколения НЕ входит в срез: reseal — отдельное
  слово; построенный корпус ждёт следующего запечатывания.
- Сети нет ни в скрипте, ни в тестах; Notion API не вызывается.
- Базы задач/вопросов VetPilot (`vetpilot-zadachi`, `vetpilot-voprosy`) в
  корпус НЕ входят: это координация, не знание (владелец разделил площадки).

## Приёмка (у каждого пункта — проверка, способная его уронить)

Новый файл `scripts/build_notion_corpus.py` (python3, stdlib only):

N1. Вход: `--snapshot-dir` (каталог со снимком `*.json` + `manifest.json`),
`--out` (каталог корпуса), `--source-commit` (hex-строка провенанса).
Для КАЖДОЙ базы манифеста, кроме исключённых (`vetpilot-zadachi`,
`vetpilot-voprosy`), sha256 файла базы сверяется с манифестом ДО разбора.
RED: один байт входного JSON изменён → exit ≠ 0, out-каталог не создан/не
изменён (fail-closed), в stderr названы база и оба sha.

N2. Каждая запись базы → один markdown `notion-vet/<база>/<id>.md`:
frontmatter (`notion_id`, `database`, `database_id`, `source_commit`,
`snapshot_sha256`, `title` и скалярные поля записи), тело — содержательные
текстовые поля («Установлено», «Открыто» и подобные непустые строки).
Пустые записи без единого текстового поля пропускаются со счётом. RED:
запись с «Установлено» → файл существует и содержит текст дословно.

N3. Детерминизм: два прогона по одному входу дают побайтово идентичные
деревья (стабильный порядок записей и полей; никаких временных меток
генерации). RED-проба: сравнение деревьев двух прогонов диффом — пусто.

N4. Выходной манифест `notion-vet/corpus-manifest.json`: `source_commit`,
per-база {rows_in, files_out, skipped}, sha256 каждого выходного md,
`excluded` с именами исключённых баз. RED: удалить один md и прогнать
`--check` → ненулевой выход с именем файла.

N5. Режим `--check`: (а) пересборка во временный каталог и побайтовое
сравнение с `--out` (детерминизм+целостность); (б) зонд: запись базы
«Правила» с наибольшей датой обязана присутствовать и нести непустое тело.
RED: порча одного выходного md → check красный.

Тесты `tests/test_build_notion_corpus.py` (pytest, фикстурный мини-снимок
в tmp_path, 6–10 кейсов): N1 fail-closed, N2 содержимое, N3 детерминизм,
N4 манифест, N5 check красный/зелёный, исключение баз задач. Каждый кейс
видан красным мутацией предмета (минимум один — в квитанции).

Прогон моста на живом стенде: снимок из `/Users/alis/vetpilot` на текущем
`origin/main` (sha в квитанции) → `corpus/notion-vet/` стенда; `--check`

корпус не затрагивается.
