# Критерии: claim-ledger пилот — утверждения заметки с версионированным evidence

Статус: написаны до реализации, 2026-08-28. Контроллер: Claude, сессия
`db23afd2-54ea-4fc4-95a2-1ca859bf4362`. Слово владельца 28.08: «Го на
P0-пилот, но не на обязательный ledger и не на production-rollout»; четыре
поправки контролёра приняты полностью; границы среза — дословно от владельца,
перенесены в криты ниже.

SDD: class **HIGH**, mode **experiment** — меняется публичный КОНТРАКТ выдачи
knowledge-rag (смысл stale-фрагмента в retrieval), поэтому криты живут здесь,
в kr; код kr в пилоте НЕ меняется (не-цель).

Источник идеи: OpenWiki grounded claims (langchain-ai/openwiki@0c5b1c0f,
PR#638) — clean-room; OpenWiki runtime не устанавливается (не-цель).

## Цель пилота

Одна живая заметка Claude-зоны получает 3–5 утверждений (claims), каждое
привязано к версии конкретного источника; изменение источника детерминированно
переводит конкретный claim в `stale` — и это доказано одним RED-прогоном.
Решение после пилота — отдельное слово владельца: оставить экспериментом,
скорректировать формат либо расширить на горячие записи.

## Формат sidecar `claim-ledger.v1`

Файл рядом с заметкой: `<note-basename>.claims.json` (в той же зоне Vault):

```json
{
  "schema": "vetclub.claim-ledger.v1",
  "note": "brain/Claude/<note>.md",
  "note_sha256": "<sha256 байтов заметки на момент серии>",
  "claims": [
    {
      "id": "clm-<8hex>",
      "statement": "одно проверяемое утверждение, дословно как в заметке",
      "status": "current",
      "evidence": [
        {"uri": "repo://<owner>/<repo>@<40-hex commit>#<путь>",
         "sha256": "<sha256 байтов файла на этом коммите>"},
        {"uri": "vault://brain/<зона>/<файл>.md@<sha256>"},
        {"uri": "runtime-receipt://<имя-receipt>@<sha256>"},
        {"uri": "web-snapshot://<наш-файл-снапшота>@<sha256>"}
      ]
    }
  ]
}
```

- `status` ∈ {`current`, `stale`, `unresolved`}. `verified` ЗАРЕЗЕРВИРОВАН и
  недостижим (контракт §4 канона: ключа controller-verifier не существует;
  строить verified-этаж запрещено до пробуждения ключа владельцем).
- Версия evidence детерминирована: для `repo://` — commit + sha256 байтов
  файла на нём; для `vault://` и `runtime-receipt://` — sha256 байтов; для
  `web-snapshot://` — sha256 НАШЕГО файла-снапшота (ETag/дата чужого сервера
  версией не являются — external-addresses правило).
- Claims создаются АВТОРОМ заметки в момент письма; ретроспективная модельная
  нарезка запрещена (не-цель, поправка 1 вердикта).

## Семантика статусов (детерминированная, без модели)

- `current`: каждый evidence разрешается и его sha256 совпадает.
- `stale`: хотя бы один evidence разрешается, но байты изменились
  (sha256-мисматч). Stale ≠ ложь: требуется повторная проверка автором.
- `unresolved`: хотя бы один evidence не разрешается вовсе (нет коммита/
  файла/receipt).
- Приоритет при смешении: unresolved > stale > current (худший статус
  побеждает — fail-closed).

## Контракт выдачи knowledge-rag (меняется ЗДЕСЬ, документом)

Фрагмент заметки, чей sidecar несёт хотя бы один не-`current` claim,
считается **stale-контекстом**: он ОСТАЁТСЯ в retrieval (выкидывание —
запрещено: пустота хуже помеченной несвежести), но потребитель выдачи обязан
(а) нести метку статуса в любом пересказе и (б) НЕ строить уверенный
synthesis на stale/unresolved-утверждении — только с оговоркой «требует
перепроверки, evidence изменился». В пилоте метка доносится байтами заметки
(блок статуса в теле при обнаружении stale) и этим контрактом; код kr,
manifest-форматы и Tool Plane не меняются (не-цели владельца).

## Критерии приёмки

- **AC-1 (серия writer):** заметка + sidecar + receipt записаны одной
  атомарной серией существующего guarded writer (лиза v1, зона brain/Claude);
  provenance-поля заметки заполнены; незакоммиченный хвост Vault доложен
  владельцу (commit — отдельное полномочие).
- **AC-2 (чекер):** детерминированный чекер (пилотная оснастка, без модели)
  читает sidecar, разрешает каждый evidence и печатает статус каждого claim;
  на свежесозданном sidecar все claims `current`.
- **AC-3 (RED):** контролируемое изменение одного evidence (фикстурная копия
  sidecar с изменённым целевым файлом) переводит РОВНО затронутый claim в
  `stale`, остальные остаются `current`; удаление evidence-файла даёт
  `unresolved`. Чекер, не умеющий краснеть, — не прибор.
- **AC-4 (границы):** ни один другой файл Vault не получает sidecar; Tool
  Plane write-tools не создаются; OpenWiki не устанавливается; retrieval-код
  kr не меняется.

## Не-цели (дословно от владельца)

Обязательный ledger для всего Vault; production-rollout; ретроспективные
массовые claims; OpenWiki runtime; Tool Plane write-инструменты; verified.

## Дельта исполнения (замечена до реализации, формат уточнён)

Sidecar — `<note-basename>.claims.md` (json в едином fenced-блоке ```json),
а не `.claims.json`: политика guarded writer покрывает только `**/*.md`
(policy.json, замерено байтами) — расширение политики на .json было бы
владельческим актом вне границ пилота. Чекер парсит первый json-фенс файла.

## v1.1 — авторский статус участвует в вердикте (слово Ali 28.08 «го», после прогона №1)

Измеренное основание (прогон №1, 28.08 вечер): чекер выводил статус
исключительно из sha-сверки evidence и игнорировал поле `status` сидекара;
опровергнутый автором клейм clm-36e09023 с намеренно замороженным пином
печатался `current`, итог `current`, rc=0 — ложно-зелёный для внешнего
читателя. Вторая дыра named в заметке пилота (блок прогона №1).

## Критерий v1.1-1

Эффективный статус клейма = худший из вычисленного по evidence и
авторского `status` сидекара (порядок тот же: unresolved > stale >
current). Печать строки клейма называет оба источника при расхождении:
`clm-…: effective=stale (computed=current, authored=stale) …`.

## Критерий v1.1-2

RED уже измерен: текущий чекер на сидекаре 7ae63c78 даёт rc=0 и
`clm-36e09023: current`. GREEN кандидата: тот же сидекар → rc=1,
`effective=stale`, строка несёт оба источника. Прочие клеймы без
расхождения печатаются как прежде (дифф вывода по ним пуст).

## Критерий v1.1-3

Смысловая дыра №1 («чекер не читает утверждение») НЕ закрывается кодом —
она закрыта процедурой перепроверки автором и остаётся named-границей в
докстринге чекера одной строкой.

## Критерий v1.1-4 (по находкам ревью R1)

Отсутствующее или неизвестное значение authored `status` — дефект
сидекара: эффективный статус такого клейма = `unresolved`, строка печати
называет причину (`authored status invalid: <значение>`), чекер не
падает. Измерено пробой на двух краях (поле отсутствует; значение вне
множества) — обе дают effective=unresolved, rc=1.
